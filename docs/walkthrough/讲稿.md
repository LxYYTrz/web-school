## 段 3 · 为什么这么设计（1 分 30 秒）

| 屏幕显示 | 你说 |
|---|---|
| 切到《代码讲解》文档 db/ 那节的设计思路段 | "接下来说清楚，**为什么是这么分的**。五个点。" |
| 第一段 | "**一、为什么要把数据分开放。**因为这个系统一天产生的东西性质完全不一样：机器人的动作是每秒十几条的连续流水，一天几十万行；产线当前是什么状态，是任何时刻只关心最新那一帧；谁登录过、谁下过指令，是只增不改的凭证。这三种东西混在一张表里，要么查历史慢，要么把无关数据越积越多。所以按性质拆开，各管各的。" |
| 第二段 | "**二、那四块是怎么分出来的。**按数据的性质分：前两块是**慢变的主数据**，建好很少改；第三块是**快变的流水**，一直在写；第四块是**只增不改的凭证**，写进去就定死了。登录账号表单独隔出去，是因为它是安全边界，跟业务数据生命周期不一样。" |
| 第三段 | "**三、高频数据要特殊照顾。**就是刚才说的机器人那块，写得最猛，所以上了时间序列的能力。" |
| 第四段 | "**四、同一件东西有两套编号。**一套是数据库内部的自增主键，另一套是系统里到处在用的、人能看懂的编码。两套之间由后端做翻译，结果在内存里缓存、定期刷新。好处是：现场新增设备只要约定好编码，采集端、消息通道、页面全都认它，数据库自增到几号完全不影响。**说白了，现场最脏最乱的设备编号问题，被隔离在数据层里了**——这也是为什么我们敢直接连真实 PLC 现场。" |
| 第五段 | "**五、约束写在数据库里做兜底。**哪些指令允许下发、产线状态允许哪些取值，这些规则在数据库这层也留了一道 CHECK 约束。好处是即便前端或后端某处校验漏了，脏数据也进不来库。代价是每次业务规则变化都要同步一条迁移脚本——这也正是这个目录里除了初始化脚本，还挂着 002 到 006 这几条的原因。" |
| 第六段 | "**六、演进只加不改。**已有的表结构和历史数据永远不删不改。需求变了就新加一条迁移脚本往上叠。新装库按文件名顺序一次性执行完，老库需要时手动补执行同一条。这样任何时候都能追溯'某个字段是什么时候、因为什么被加上的'。这是数据库设计最基本的一条规则，我们整套库都是这么演进的。" |

**提示：**第四条最容易讲飘，记住一句就够：**"外面用人看得懂的编码，里面用自增序号，中间翻译一次。"**第三条和第六条是"性质"层面的，可以讲快点。

## db/ 备用 · 被追问时怎么答

下面这几段不主动讲，只在被问到时用。

**问：为什么不直接用 MySQL 或者普通 PostgreSQL，一定要 TimescaleDB？**

**答：**机器人数据是 10Hz，一台一天 86 万行。TimescaleDB 就是在 PostgreSQL 上加的一层时序能力，它自动按时间切块存放，查历史只扫相关的那一块；另外还自带冷数据压缩和过期清理策略。普通表也能跑，但量上来以后查询和磁盘都会出问题，而这两个能力我们需要自己写扩展才能有。

**问：两套用户表是不是重复了？**

**答：**分工不同。`users` 挂的是完整的角色-权限模型，配着一整套角色、权限点和关系表；`app_users` 是后来单独拆出来的，实际登录校验走的是它，只用三级权限数字。指令审计和 AI 那块引用操作人时用的是前者。这是项目从原始版本演进过来的痕迹，不是设计失误。

**问：控制指令的"幂等键"是干什么的？**

**答：**MQTT 是"至少送达一次"，同一条指令有可能到两次。如果不做防重，产线可能被启动两次。幂等键就是这条指令的唯一编号，发出去的时候带着它，回来的时候也带着它，数据库里一比对就知道是不是同一条，只执行一次。

**问：为什么急停不在系统里？**

**答：**急停必须是硬件回路，网页永远不做急停。系统里能做的只有"软控制"，而且真正能不能执行，最终否决权在 PLC 自己的联锁逻辑手里——这也是为什么指令回执里会有"拒绝"这个状态。

**问：表结构能改吗？**

**答：**不能改，要改就新开一条迁移脚本。这是为了保证任何时候都能追溯"某个字段是什么时候、因为什么被加上的"，同时保证新装的库和老库结构一致。

**问：15 张表是不是太多了？**

**答：**分来看不少，其实高度重复——第四块那 3 张表，本质上是同一类东西的三个版本：一张存流水、一张存当前、一张存留痕。分开的理由只有一个：它们的写入频率和查询方式完全不同，混在一起会把高频查询拖慢。真正有独立生命周期的其实只有五类，也就是开头那五个问题。

## deploy/ 备用 · 被追问时怎么答

下面这几段不主动讲，只在被问到时用。

**问：为什么不用一台服务器全跑了，要分两台？**

**答：**三个原因。产线不能依赖外网，断网时采集和控制必须在本地闭环；10Hz 的数据流低配云服务器扛不住；新增产线时只加工控机，云端零改动。本质是**把不可接受的风险（产线停摆）留在本地，把可以暂时不可用的（外部查看）放在云端**。

**问：为什么工控机不干脆也放云上？**

**答：**技术上可以，但那样断网整条产线的数据就断了，违反"产线照常运行"这条底线。而且采集器要直连产线内网的 PLC，网关到工控机在同网段，配置最简单。

**问：SSH 隧道会不会不稳定？**

**答：会有风险，所以做了三件事：用密钥免密登录；加保活参数，15 秒一次心跳，连续 3 次没回应就断开重连；再配看门狗脚本，断线自动拉起——仓库里就是 scripts/tunnel-keepalive.ps1。巡检这里还踩过一个坑：原来用 ssh 过去探活，但 ssh.exe 在 SYSTEM 身份下会间歇性卡死，会把好端端的隧道误杀，所以改成了端到端实测——隧道进程在不在 + 公网接口有没有响应，两项全过才算健康。SSH 隧道换成 frp 也能平替，转发语义一样，代码零改动。**

**问：公网为什么还是 HTTP，HTTPS 没配吗？**

**答：**配置和证书目录已经预留好了，Nginx 里 443 的端口和证书挂载位置都写好了，取消注释就能开。当前是过渡状态，正式上线前会补上。

**问：开发机那份三合一的 compose，生产上能不能直接用？**

**答：不能。生产切了三刀：数据库从中枢挪到工控机本地原生安装；工控机容器里只留消息队列和缓存；所有端口从“对外开”改成“只绑本机”。云端那份最后只剩一个 Nginx 容器。**

**问：容器里的数据怎么保证不丢？**

**答：中间件（消息队列、缓存）的数据都放在具名卷里，容器删了卷还在。数据库那边是工控机原生安装的 PostgreSQL，不在容器里，所以得另外做数据库导出备份，备份到云端或离线盘。这一条在上线检查清单里，还没全部落实。**

## 段 2 · 现场版采集器：它到底干了什么（1 分 30 秒，全篇重点）

| 屏幕显示 | 你说 |
|---|---|
| 切到《代码讲解》文档 edge/ 那节 plc_collector.py | "**这是整个系统里唯一一段跟真实设备对话的代码。**它就干四件事：连上设备、读点位、把点位翻译成统一的格式、发出去；另外还负责接网页上下来的指令，写回设备。" |

| — | "**逐点读是有代价的：17 个点就是 17 次请求，一秒 5 轮。**好处是容错特别细——某一个点读失败，只有这一个点变成'没读到'，其余 16 个点照常上报，**整帧数据不会因为一个坏点丢掉**。" |

| — | "**PLC 没连上的时候也一样回'拒绝'**，不写、不回成功。" |
| 指单实例锁那段 | "**最后是这一块最硬的一道防线：同一台机器只允许一个采集器。**现场那个服务端块只接受一条连接，第二个永远连不上；更隐蔽的是两个采集器用同一个名字连消息代理，会**互相把对方踢下线**，表现是'状态偶尔能上来、下行指令一条都收不到'。所以程序启动先抢一把文件锁，抢不到就直接退出；万一还是起了两个，名字里带上进程号，至少不互相踢。**这个坑我们现场踩过，排查了很久。**" |

| — | "**发出去的时候用了三个机制**，快速带过：保留消息让后端晚启动也能立刻拿到当前状态；遗嘱消息让程序崩了以后代理自动发'离线'，不用写心跳轮询；可靠性分两档，关节这种高频数据丢一帧无所谓，状态和指令不能丢。" |

## edge/ 备用 · 被追问时怎么答

下面这几段不主动讲，只在被问到时用。

**问：某个点读不到，会不会整帧数据都丢了？**

**答：不会。**采集是**逐点读**的，一个点失败只影响这一个点被记成空值，其余点照常上报，页面显示"—"。这也是我们特意不用"一次性读一整段"的原因：代价是请求数多（17 个点就是 17 次请求，一秒 5 轮），换来的是容错粒度细、坏点不拖垮整帧。**顺带说清楚：代码里那段注释写的是"把同区段合并成一次请求"，实际实现并没有做合并，是一处注释与实现不一致的历史遗留，不影响功能。**

**问：为什么读失败不直接填 0？**

**答：0 和"没读到"是两件事。**对传感器和灯色这些点，0 是有意义的真实值——确实是没料、确实是绿灯。填 0 等于往界面上放假数据，操作员会以为现场真的这样。所以没读到就是空值，页面显示横杠。零值的问题在测试里也专门覆盖过：用 `or` 兜底的写法会把 0 吞成别的值。

**问：清单上有 7 个指令，为什么只能执行 4 个？**

**答：因为现场 PLC 只开放了 4 个写入点。**指令清单是**契约层**的，保留完整性是为了将来现场加了寄存器直接能用，不用改数据库和前端。但现在点下去，采集器会明确回"拒绝"并说明"现场 PLC 无对应寄存器"。**这里绝对不能假装成功**——操作员看到成功就以为产线动了，实际什么都没发生，在产线上这很危险。三个没有寄存器的指令是：复位、换型、清报警。

**问：为什么写指令只写一次，不回写 0？**

**答：现场 2026-10-16 确认，PLC 在完成动作之后会自己把那个寄存器清零。**最早的设计是模拟"按一下按钮"——写 1、等 100 毫秒、再写 0。现在只写一次，因为两个写者抢同一个寄存器，采集器那迟到的"写 0"会把 PLC 刚写好的值覆盖掉。另外传送带是电平型（写正转就一直转，得再写一次才停），和启动、停止那种脉冲型语义本来就不同。

**问：为什么不能把两个采集器合成一个，用配置切换？**

**答：它们面向的场景不同。**现场版要处理工业协议、字节序、缩放、点位表、半开半合的容错；开发版是造假数据给人看动画的，代码风格完全不同。硬合在一起，开发机每次跑都要带着一套现场参数和一堆分支。**更重要的是这个目录里的文件是按"现场交付"组织的：现场只需要知道改接线表，其余文件不用看。**合并反而会让现场多一份心智负担。

**问：采集器崩了，页面会怎么样？**

**答：自动变离线。**采集器给消息代理留了一条"遗嘱"——它异常消失时，代理自动替它发一条离线状态，产线离线状态因此自动产生，不需要写心跳轮询。正常退出时遗嘱不会触发，所以程序在退出前会主动发一条离线。另外在线状态每 30 秒重发一次，因为后端把它存进缓存时设了 5 分钟有效期，只在启动和退出各发一次的话，跑满 5 分钟后缓存就过期，页面会永远看不到在线。

**问：为什么现场要单独搞一个只读探针，直接用采集器不行吗？**

**答：能用，但不该那么用。**探针的价值在于它的安全边界是**文件级的**——整份代码只有一个读函数，没有任何写调用。现场验收阶段只需要"看清现状"，没必要为了看一眼状态去动产线的寄存器。**而且现场那个服务端块只允许一个客户端，单独跑任何工具之前都必须先停采集器。**这条在交付时讲清楚，能避免现场直接把自己的数据源顶掉。
