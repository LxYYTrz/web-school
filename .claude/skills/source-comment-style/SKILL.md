# 源码注释约定

本 skill 保存用户已经确认的注释格式。用户后续调整这套格式时，先更新本文件，再按更新后的约定修改源码；普通业务功能变化只需更新相关注释，不要擅自扩大本规范。

## 每行代码下面写两行注释

1. 第一行说明这行实际做了什么，涉及什么业务数据，结果保存在哪里或影响什么。
2. 第二行解释这行出现的变量、对象、方法、参数、属性和必要的特殊写法。说明它们是什么、来自哪里、在这里有什么用途。

两行都紧跟源码，使用该语言原生的注释语法。不要加“整体作用”“组成说明”“关键字”等固定前缀。常规的等号、点号、括号和逗号无需解释；只解释影响理解的不常见写法，例如解构、可选链、展开、SQL 参数占位符、Vue 指令。

说明标识符时先查实际定义、导入或调用方。外部方法查本机依赖实现或对应版本文档。区分项目自己定义的变量、第三方 API、框架注入对象及外部报文字段。不能把 `rr` 仅解释为“变量”，也不能把一行注释写成“给 rr 赋值”“调用方法”“处理数据”。需要解释 `rr` 保存哪次请求的响应、调用的方法完成什么、参数值来自哪里。

同名标识符以当前位置的作用域为准，不跨函数套用含义。接口字段、对象字面量属性和字典键需要结合对应业务契约说明。无法确认的含义保留可证实的描述，不编造设备地址、单位、业务约束或执行成功状态。

括号、花括号等独立结构行不讲解常规符号；说明该行结束的是哪个方法、对象或功能分支，以及这部分与上下文的关系。已有注释、空行不继续递归追加说明。

## 每段功能前后写说明

按实际功能划分段落，例如建立连接、校验登录信息、查询记录、组装报文、刷新界面。函数、方法、独立流程或一个有明确用途的配置组都可以成为一段。避免每个语句都额外包成一个功能段，也不要把整个文件只标成一个笼统大段。

- 段前说明这段准备实现什么功能，必要时交代输入和使用场景。
- 段后说明这段实现了什么，得到了什么结果、返回了什么，或供后续哪部分使用。
- 函数定义的段后描述函数的职责，不写成“函数已经执行成功”。有失败路径时说明按实际分支返回、拒绝或抛错。
- 段前、段后同样不使用“整体作用”等固定标签，直接写自然的中文说明。

## 用户确认的示例

```python
# 这一段创建 PLC 通信客户端，并尝试建立 TCP 连接，为后续读取寄存器准备通信通道。

cli = ModbusTcpClient(host=HOST, port=PORT, timeout=2)
# 创建用于连接 PLC 的 Modbus TCP 客户端，保存到 cli，供后续连接和读取使用。
# cli 是保存客户端对象的变量；ModbusTcpClient 是从 pymodbus.client 导入的客户端类；host=HOST 指定目标 IP，当前为 "192.168.10.31"；port=PORT 指定目标端口，当前为 503；timeout=2 设置通信超时时间为 2 秒。

connected = cli.connect()
# 尝试连接 PLC，并把是否连接成功的结果保存到 connected。
# connected 是保存连接结果的变量，True 表示成功，False 表示失败；cli 是上面创建的通信客户端；connect 是客户端提供的建立连接方法。

# 这一段完成客户端创建和连接尝试，得到客户端 cli 与连接结果 connected；后续代码根据连接结果决定是否继续读取 PLC 数据。
```

## 文件格式和验证

注释写在手写源码中，不另建一套逐行说明文件。生成的 dist、依赖、二进制、锁文件不逐行注释。严格 JSON、CSV 等格式不能硬插注释或虚构字段。

保留运行行为、编码和原有有效的注释；Windows PowerShell 的中文脚本保留或使用 UTF-8 BOM。脚本的 shebang 和 HTML 的 doctype 必须保持为文件首行；文件级说明放在它们后面，也不能落入紧随其后的多行文档字符串或 HTML 注释内部。不要把注释插进多行字符串、HTML 属性列表、显式续行等会改变语义的位置；在语法完整的相邻位置解释这些连续内容。允许在确保语义等价时把多行标签属性整理成一行。

验证时检查：每行的两条说明是否相邻；解释是否符合局部定义；功能段前后是否讲清用途与结果；是否仍有机械复述或错误的“关键字”说明；是否无意改动了字符串或代码。可以将注释前后的 Python AST、TypeScript/JavaScript 去注释语法树与字符串字面量逐项对比，以发现注释进入多行字符串的问题。运行涉及语言的构建、语法检查与已有必要测试。不要为注释工作修改业务功能或新增测试体系。
