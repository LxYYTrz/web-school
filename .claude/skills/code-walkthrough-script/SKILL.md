# 代码讲解稿写作规范

把一个代码模块写成**能照着念的讲稿**。读者是讲解者本人（边讲边看稿），听众是不懂技术的业务方。

**产出是两篇配套文档，顺序固定：先《代码讲解》（展示用），后《讲稿》（自用）。** 详见「工作顺序」一节。

**本项目的使用场景**：主线讲解约 20 分钟，听众会随时打断提问。《代码讲解》要保留足够细节供现场展开；《讲稿》把 20 分钟主线放在最前面，后续逐模块内容作为追问时的扩展稿。不要为了缩短主讲而删掉展示文档中的依据和解释。

## 核心形态：对照表

讲稿的主体是**两栏对照表**，不是连续段落：

| 屏幕显示 | 你说 |
|---|---|
| 切到《代码讲解》文档 db/ 那节的四块表清单 | "先说规模：一个数据库、两个 schema、15 张表……" |
| 手指停在 `user_line_scope` | "客户只能看自己名下的产线，靠的就是这张表在后端查询时做过滤，不信前端传参。" |

**为什么必须是两栏**：讲解者需要同时看到「此刻屏幕上是什么」和「此刻该说什么」。写成段落就做不到——段落读起来是线性的，人会失去"讲到哪了"的画面感。

左栏必须具体到**动作和位置**（"手指停在 XXX"、"切到某目录展开 7 个文件"），不能写"展示代码"这种空话。
左栏引用的表、图片、标题或文件必须在当前投屏材料或当前仓库里实际存在；没有准备截图，就指向《代码讲解》里真实可见的目录导航表或模块标题。

## 文档结构模板

下面是逐模块扩展稿的模板；多模块现场汇报先在《讲稿》开头放一条控制总时长的主线，再把这些扩展稿留给提问时翻查。

```
<title>讲稿</title>

<h1>模块名 —— 展示 / 讲稿对照</h1>

<p>用法：左边一栏是屏幕上的东西，右一栏是你嘴上说的话。讲到哪儿就看哪一行。</p>
<p>铁律：不要说「<黑话>」——那是文档词，观众听不懂，你自己也讲不顺。一律说「<人话>」。</p>
<p>总时长：X~Y 分钟。段 0 必讲，段 N~M 按现场时间取舍。</p>

段 0 · 开场：<N> 个 <锚点> 先记住（30 秒）      ← 必讲，且是记忆锚点
  [对照表]
  [锚点表：问题 | 靠什么回答 | 一句话答案]      ← 核心，单独成表

段 1 · <内容>（1 分 30 秒）                    [对照表]
段 2 · <内容>（30 秒，可选）                    [对照表]
段 3 · <内容>（1 分 30 秒）                    [对照表]
段 4 · <内容>（45 秒）                          [对照表]
段 5 · 收尾（10 秒）                            [对照表]

备用 · 被追问时怎么答                          ← 不主动讲，只备着
```

每段对照表下面跟一段 `<b>提示：</b>`，写**动作提醒和防串台锚点**，不是重复内容。

## 左栏写"此刻屏幕上是什么"，不是"把代码贴进来"

- 正确：切到《代码讲解》文档 deploy/ 那节 / 指 `deploy/nginx/cloud.conf` 的 `upstream` / 切到 `deploy/README.md` 的验证步骤
- 错误：在左栏塞一大段代码块、拓扑图 ASCII、故障日志

**理由**：代码本来就投在屏幕上，讲稿再抄一遍是重复劳动，还让讲稿变得难读。左栏的任务是**当导航**，不是当展示。

讲解时要用到的图（拓扑、端口表、代码片段）应该另外准备成展示材料，讲稿只写"看哪儿"。

## 硬性要求

### 1. 段 0 必须给"记忆锚点"

讲解者最大的风险是**自己没真懂**，讲到一半卡住。段 0 就是要给他一张能随时回来看的骨架。

骨架必须满足：
- 是**问题**，不是"域"、不是"分层"、不是任何文档自造词
- 数量少（4~6 条）
- 每条都有"一句话答案"
- 后面所有段落都能挂回这 N 条

反例（会害了讲解者）："四个域各管一摊" —— 讲解者自己都会卡壳。
正例："整套库表设计，说到底就是在回答四个问题，外加一个登录账号。"

**自检**：把黑话词全部找出来（域、层级、体系、抽象、编排、闭环……），凡是听众不懂的一律换成大白话。

### 2. 必须防串台

逐项讲解的段落（尤其一串文件、一串模块），左栏要写死**顺序锚点**：

> 顺序固定背下来：初始化 → 登录账号 → 扩指令清单 → 放状态 → 加传送带 → 校正等待机器人状态 → 删视觉 → 说明书

> 念到哪个就指着哪个文件，别回头找。

### 3. 主动抢话

把"评委/听众最可能问、且自己知道答案"的问题**提前塞进正文**，不要留到问答环节。

典型："这也是我们为什么选 TimescaleDB 而不是普通 PostgreSQL 的原因……"

### 4. 诚实标注不确定的

发现项目里有历史遗留、命名不一致、看起来奇怪但确实存在的东西，**主动说明**，显得真懂，也提前堵住质疑。

典型："系统里其实有两张用户表……这是项目从原始版本演进过来的痕迹。"

### 5. 备一节"被追问时怎么答"

放最后，不主动讲。至少准备：
- 选型类（为什么用 X 不用 Y）
- 看起来重复/奇怪的地方（为什么有两张表）
- 关键机制（幂等键是干什么的）
- 安全边界（为什么急停不做）
- 数量质疑（是不是太多了？）

### 6. 不念字段名

面向不懂技术的听众时，主体只讲「有哪些东西、各自干什么、为什么这么设计」。具体字段、参数、地址，被追问再翻代码。

例外：如果模块本身就是"讲数据结构的"（比如 db/ 讲库表设计），那表名要出现，但**字段仍然不念**。

### 7. 数字要具体

"写得最猛"、"量很大"这种没信息量的说法，替换成可算的数：
"机器人数据 10Hz，一台机器人一天就是 86 万行，多台机器再乘上去。"

### 8. 风险点要讲

凡是"做错了会出事"的设计，必须讲出来，这是分量最重的内容：
- 幂等键防重复执行
- 无点位回"拒绝"绝不假装成功
- 审计表独立于业务表
- 急停是硬件回路，网页永不做

## 语气要求

- **口播稿用引号包起来**，明确这是直接念的话
- 句子要短，能一口气念完
- 不要"首先/其次/然后"堆叠，用具体内容承接
- 关键结论用 `<b>` 加重（念的时候要重读的那句）
- 数字、路径、字段名用 `<code>` 包起来

## 写作前核对当前事实

- 先看当前分支的文件清单和对应源码、README，再核对《代码讲解》和《讲稿》。文档中指向的文件、截图、表格和配置地址必须真实存在。
- 仓库目前以原生服务为部署目标：工控机基础服务由 Windows 服务管理，后端与采集器原生运行；云服务器使用原生 Nginx。旧 Compose 与容器故障记录只能作为历史背景，不能说成当前仓库的启动方式。线上是否已完成迁移要单独核实，不能从仓库目标反推线上现状。
- 技术数字要能追溯到代码、配置或实测。不能把“减少数据库往返”写成未经测量的“磁盘压力降低两个数量级”；`public` 和 `app` 是 PostgreSQL schema，不是数据库分区。
- 主讲时长要按真正要念的字数和切屏动作复核。即问即答场景下，主线可短，细节保留在展示文档和扩展稿里。

## 两篇文档必须分开（铁律）

这是两篇**用途完全不同**的文档，绝不能混：

| | 《代码讲解》 | 《讲稿》 |
|---|---|---|
| 定位 | **展示用** —— 投屏给听众看的 | **演讲者自用** —— 自己对照练习的演讲词 |
| 内容 | 代码结构事实：有什么文件、各自干什么 | 嘴上说的话 + 此刻该看哪儿 |
| 用词 | 项目自己的客观术语（"四个域""编排"） | 讲给听众听的通俗话（"四个问题"） |
| 折叠 | 每个标题行要带说明，折叠时也看得到 | 按段组织，对照表 |

**关键推论：两篇文档允许用不同说法，不要强行统一。**

- 讲稿为了好讲，可以把"四个域"翻译成"四个问题"——这是**演讲技巧**。
- 但《代码讲解》是客观展示，域该怎么分就怎么分，**不要把口播框架灌进去**。
- 如果讲稿里的通俗说法和《代码讲解》的术语对不上，**在讲稿左栏补一句指路**（"切到《代码讲解》文档 db/ 那节的四块表清单"），让听众能对上就行。
- 反过来，**不要为了让两篇一致，去改《代码讲解》的术语**——那是展示文档，不是稿子。

**曾经犯过的错**：为了统一口径，把《代码讲解》里 db/ 的小标题从"一、账号与权限"改成"问题一：谁在用、能看什么"，还把正文里的"四个域"改掉。结果展示文档变得半文半白，讲解时反而更绕。**改讲稿，别改展示文档。**

## 工作顺序（铁律）：先《代码讲解》，后《讲稿》

写任何一个模块，**必须按这个顺序，两步都要做**：

```
第 1 步  《代码讲解》  ——  把这个模块的展示内容写开
         ├ 模块标题下的总述段（这一块整体是什么、为什么这么切）
         └ 每个子项一条正文（这个文件具体是什么、里面有什么细节、为什么这么设计）
         写完这个模块里不能还有"待展开"三个字

第 2 步  《讲稿》      ——  再写这个模块的演讲词
         左栏才有东西可指："切到《代码讲解》文档 XXX 那节 / 指 XXX"
```

**只写讲稿、不写《代码讲解》= 讲稿的左栏指不到东西，讲的时候观众眼前是空的。**

**曾经犯的错**：用户说"写 deploy/ 的讲稿"，我一头扎进讲稿，把《代码讲解》冷落了半天，deploy/ 那节全是"待展开"，讲稿左栏写"切到《代码讲解》文档 deploy/ 那节"——那儿什么都没有。**讲稿是第二步，不是第一步。**

### 第 1 步的正文怎么写

- **总述段**放在模块标题正下方：这块整体是什么、为什么这么切、有什么必须记住的边界
- **每个子项**（文件/目录）一条或几段正文，不要只留一句标题
- **技术细节要翻译成"为什么"**：不是罗列配置项，而是每个配置背后在防什么、解决什么问题
- **主动写进"边界"和"单点"**：云端不跑什么、什么断了会挂、哪些是待办
- 写完检查一遍：该模块里还有没有"待展开"？有就是没写完

## 写飞书文档

- 身份：`--as user`
- 格式：`--doc-format xml`（对照表、`<code>`、`<b>` 都更可控）
- 从零新建文档时一次写入完整内容；已有文档不要用 `overwrite`
- 局部改：`block_replace` / `block_insert_after` / `str_replace`
- 改完要 `docs +fetch` 回读校验标题层级和表格数
- 内容文件写在 cwd 下用相对路径（`@` 只接受相对路径），用完删掉

### ⚠️ 不要 overwrite 整篇

讲稿文档是**多模块累积**的（db/ 讲稿 + deploy/ 讲稿 + …在同一篇里）。

- **《讲稿》是累积文档**：新增模块一律用 `append`（等价于 `block_insert_after --block-id -1`），**不要 overwrite**。
- **《代码讲解》是就地修改**：改某个模块用 `block_replace` / `block_insert_after` 定位到那个模块的 block id，**不要 overwrite**（会冲掉其它已写好的模块）。

**曾经犯的错**：写 deploy/ 讲稿时用 `overwrite` 整篇重写，把 db/ 那份讲稿冲掉了，用户发现后才发现。**写新模块用 append。**

### 批量改 block 的做法

要改多个 block 时，把 (block_id, 内容文件) 写进临时目录，用循环逐个调 `block_replace --content @文件`。
注意：cmd/PowerShell 直接传长文本参数会被引号和换行吞掉，**内容一律走 `@文件`**。

## 迭代方式

写完一个模块后，**根据用户的反馈修改本 SKILL**。用户提出新要求时：
1. 立刻按新要求改这两篇文档
2. 同时把新要求补进本 SKILL 的"硬性要求"
3. 说明改了什么

这样下一个模块直接按最新规范写，不用重复纠正。
